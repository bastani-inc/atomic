# Changelog

## [Unreleased]

### Changed

- A transaction with `relaxedDurability` runs with `synchronous_commit` off, set inside the `BEGIN` the adapter already sends, so it costs no extra round trip. Its commit returns without waiting for the disk. The setting ends with the transaction ([#6633](https://github.com/bastani-inc/atomic/pull/6633), [#6560](https://github.com/bastani-inc/atomic/issues/6560)).
- A transaction that sends a wake-up notification no longer holds up every other one that does. PostgreSQL takes one server-wide lock for every commit that sends a notification and holds it until that commit is written to disk, so those commits ran one at a time. The adapter now sends the notification right after the commit, in a short transaction of its own that does not wait for the disk, in the same round trip as the commit. When several commits in one process send the same notification within 5 ms, it goes out once after them. In a test on PostgreSQL 16 with 50 Intercom senders waking brokers at once, commits went from 158 to 286 per second up to 1,408 to 2,182 per second, and the median commit from 147 to 296 ms down to 18 to 30 ms. With 200 senders, commits went from 215 to 234 per second up to 2,037 to 2,640, and the median from 673 to 804 ms down to 52 to 69 ms. Each range covers 3 rounds that alternated the two versions on a busy machine. A notification lost between the two transactions only delays its listener until its next poll, as one lost while the listening connection is down already did ([#6655](https://github.com/bastani-inc/atomic/pull/6655)).

## [0.10.11-alpha.2] - 2026-11-26

### Changed

- Opening a database also reads the list of Atomic's tables and their recorded versions, in the same round trip as the server version. The first store opened on the database uses them instead of reading them again, so opening it takes one round trip less ([#6606](https://github.com/bastani-inc/atomic/pull/6606), [#6560](https://github.com/bastani-inc/atomic/issues/6560)).
- Prepared statements now turn on behind PgBouncer 1.21 or later when its `max_prepared_statements` is above `0`, which is PgBouncer's default from 1.24. Atomic checks this on its first connection without an extra round trip. PgBouncer 1.26 and later report it when a client logs in. For 1.21 to 1.25 Atomic checks whether PgBouncer renamed a test statement, then removes it. Behind Supavisor, older PgBouncer releases, PgBouncer with `max_prepared_statements = 0` and any pooler Atomic cannot identify, they stay off. The same check now also notices a pooler on a port other than `6432` or `6543`, when the pooler hands out its own cancel keys, as PgBouncer does, and turns prepared statements off there too. A pooler on another port that does not hand out its own cancel keys goes unnoticed, so set `listenUrl` or `maxPreparedStatements: 0` for it. A `maxPreparedStatements` you set still wins ([#6604](https://github.com/bastani-inc/atomic/pull/6604), [#6560](https://github.com/bastani-inc/atomic/issues/6560)).

## [0.10.11-alpha.1] - 2026-11-25

### Breaking Changes

- This package now needs Node.js 24.20.0 or newer, in the Node.js 24 LTS line (`engines.node` is `>=24.20.0`, up from `>=22.19.0`). Check with `node --version`, and upgrade from [nodejs.org](https://nodejs.org/en/download) or with `nvm install 24`, `fnm install 24`, or `mise use -g node@24`. Node.js releases before 24.15.0 bundle a SQLite version with a [bug that can corrupt](https://www.sqlite.org/wal.html#walresetbug) a database opened by a writer and a reader at once, and Node.js 24.17.0 through 24.19.0 reject valid certificates for IPv6 addresses ([nodejs/node#64145](https://github.com/nodejs/node/pull/64145)) ([#6579](https://github.com/bastani-inc/atomic/pull/6579)).

### Added

- New connection options: `readerMaxConnections` (default `2`, where `0` turns the separate read pool off), `connectTimeoutMs` (default `10000`), `idleTimeoutMs` (default `300000`) and `keepAliveIdleMs` (default `60000`). The storage guide's [tuning section](https://docs.bastani.ai/storage#tuning-for-many-concurrent-agents) shows how to size them for many agents ([#6588](https://github.com/bastani-inc/atomic/pull/6588), [#6560](https://github.com/bastani-inc/atomic/issues/6560)).
- The `maxPreparedStatements` option, default `256`, keeps statements a process sends repeatedly prepared on each connection, so the server parses and plans each one once instead of on every call, at no extra round trip. Atomic turns it off when it detects a transaction pooler, which it assumes when `listenUrl` is set or the port is `6432` or `6543`. A call that a pooler refuses for a missing or duplicate prepared statement, or that a schema change made stale, runs again on a new connection ([#6588](https://github.com/bastani-inc/atomic/pull/6588), [#6560](https://github.com/bastani-inc/atomic/issues/6560)).

### Changed

- Calls that cannot conflict, such as writes to different sessions and read-only transactions, run at the same time on separate connections. A transaction sends its first reads with its `BEGIN` and its last writes with its `COMMIT`, so saving entries to a session takes 2 round trips instead of 7 or more. If the server refuses one of those first reads, for example because it waited too long for a lock, the transaction runs again ([#6588](https://github.com/bastani-inc/atomic/pull/6588), [#6560](https://github.com/bastani-inc/atomic/issues/6560)).
- `openReader()` returns a read handle on a separate pool of up to 2 connections, so reads do not wait for connections that writes are using. Reader connections show as `atomic-reader` in `pg_stat_activity`. Closing the database also closes its readers ([#6588](https://github.com/bastani-inc/atomic/pull/6588), [#6560](https://github.com/bastani-inc/atomic/issues/6560)).
- Every database a process opens with the same URL, role, password, schema and pool options shares one pool, one reader pool and one listening connection. A process that opens a session store and an Intercom broker, or several session stores, now holds one set of connections instead of one per store. The last database to close closes them. If `password` is a function, Atomic calls it once when the database opens, to tell credentials apart ([#6588](https://github.com/bastani-inc/atomic/pull/6588), [#6560](https://github.com/bastani-inc/atomic/issues/6560)).
- A pool's last connection stays open for 5 minutes after the pool's last call instead of 10 seconds, with TCP keepalive after 60 seconds, so a call after a pause skips the connection and TLS handshakes. Connections opened for a burst still close after 10 seconds idle. Unused connections no longer keep the process from exiting ([#6588](https://github.com/bastani-inc/atomic/pull/6588), [#6560](https://github.com/bastani-inc/atomic/issues/6560)).
- Opening a database reads the server version and the schema that holds Atomic's tables in one query instead of two ([#6588](https://github.com/bastani-inc/atomic/pull/6588), [#6560](https://github.com/bastani-inc/atomic/issues/6560)).
- A read-only transaction returns its connection to the pool as soon as its `COMMIT` is sent instead of when it is answered. The connection sends the next transaction's statements after the `COMMIT`, so reads made one after another reuse one connection instead of opening a second one, whose handshakes cost several round trips ([#6599](https://github.com/bastani-inc/atomic/pull/6599), [#6560](https://github.com/bastani-inc/atomic/issues/6560)).
- A database now tells Atomic which server, database, role and schema it reaches. Atomic uses this to recognize two handles on the same database, and copies a session fork between them inside the database instead of staging it through another table ([#6596](https://github.com/bastani-inc/atomic/pull/6596), [#6560](https://github.com/bastani-inc/atomic/issues/6560)).

## [0.9.90] - 2026-11-19

### Added

- Connections through an HTTP proxy: where the only way out is a proxy that opens `CONNECT` tunnels, such as a sandbox's, every connection to PostgreSQL (the pool's, the wake-ups connection and cancel requests, and their reconnects) tunnels through the proxy `HTTPS_PROXY` names, then `ALL_PROXY` or `HTTP_PROXY`, unless `NO_PROXY` exempts the database host, as for Atomic's other HTTPS clients; a database on this machine is reached directly. The new `proxy` option, an `http://` or `https://` URL or `"none"`, overrides the environment, and SDK callers can pass `socket`, a function that opens each connection, for a custom transport. TLS still runs end to end with the server: with the default `verify-full` (or `require` without `sslrootcert`) it checks the certificate against the database's host name, so the proxy sees only encrypted traffic, cancel requests included. `verify-ca` does not check the host name, so it keeps the proxy out only with an `sslrootcert` CA that signs your database servers alone; `prefer`, `allow` and `disable` let a proxy read the traffic. A proxy that refuses the tunnel fails the open with `StorageUnavailableError` naming the proxy, without its credentials, and the `host:port` it refused, and the warning an open prints while it retries a proxy that cannot be reached names the proxy rather than the database server. If you already set `HTTPS_PROXY` (or Atomic's `httpProxy` setting) and reach a remote database directly, its connections now go through that proxy: add the database host to `NO_PROXY`, or set the `proxy` option to `"none"`, to keep them direct ([#5473](https://github.com/bastani-inc/atomic/issues/5473))

### Fixed

- A URL that names no host, used with `PGHOST`, now gets the same default `sslmode=verify-full` as a URL naming that host when `PGHOST` is not this machine, instead of connecting without TLS. A URL that names this machine in another spelling, such as `127.1`, `localhost.` or `[::ffff:127.0.0.1]`, no longer gets a default `sslmode=verify-full`, which a local server without TLS refused: it is treated as this machine, like `localhost` and `127.0.0.1` ([#5473](https://github.com/bastani-inc/atomic/issues/5473))
- Wake-ups no longer turn off for the rest of the process when the check of the listening connection had to open a new pool connection that took longer than 2 seconds, as through a slow proxy or while a cloud identity issues its first token. The check now waits for its notification only once it was sent ([#5473](https://github.com/bastani-inc/atomic/issues/5473))
- Proxy tunnels no longer fail when the proxy sends an informational reply such as `103 Early Hints` before the final `200`. The 16 KiB header limit and 8-second timeout cover all replies together, not the database traffic that follows. A proxy whose connection ends right after a CR byte of its answer is reported as closed, which the open retries, instead of as an answer that is not HTTP, which it never retries. A CR inside a header field that no LF follows is read as a space, so the answer's final status decides. A CR in a status line is still refused, and a CR where `HTTP/` should start an answer is now refused at once instead of after the 8-second deadline ([#5565](https://github.com/bastani-inc/atomic/issues/5565), [#5670](https://github.com/bastani-inc/atomic/issues/5670))

## [0.9.88] - 2026-11-16

### Added

- `@bastani/atomic-storage-postgres`, a PostgreSQL storage adapter for Atomic sessions, workflow journals, and Intercom, installed with `atomic install npm:@bastani/atomic-storage-postgres`. It keeps a pool of up to 8 connections per process, bounds every statement with a 30-second statement timeout, and works through transaction-mode poolers such as PgBouncer. The password comes from the selection's `secrets` and is read again for each new connection, so a rotated password file is picked up without a restart; a URL that carries a password is refused. Lock conflicts, cancelled statements, and refused or lost connections are reported as `StorageTransientError`, and a call that wrote nothing runs again. PostgreSQL 14 or newer is required ([#4793](https://github.com/bastani-inc/atomic/issues/4793))
- Cloud IAM authentication for the PostgreSQL adapter: set `auth` to `"azure-entra"`, `"aws-iam"` or `"gcp-iam"` and each new connection signs in with a short-lived token from the cloud's own SDK (`@azure/identity`, `@aws-sdk/rds-signer` or `google-auth-library`, installed beside the adapter as an optional peer dependency) instead of a stored password. Tokens stay in memory, each token request is time-limited, and a failure names the package to install or the SDK's reason without showing a token. The README lists the least-privilege role for each cloud ([#4793](https://github.com/bastani-inc/atomic/issues/4793))
- Wake-ups through `LISTEN`/`NOTIFY`: the adapter keeps one listening connection per process and exposes it as `notifications` on the opened database, so worker hosts and Intercom brokers learn about new work at once instead of at their next poll. Their polls stay, so a dropped listening connection or a transaction pooler only makes them slower, never loses work. Through a transaction pooler, set the new `listenUrl` option to the server's direct endpoint; otherwise the adapter detects that notifications do not arrive, unlistens, and uses polling alone for the rest of the process, so it leaves no `LISTEN` on the pooler's server connections. A listening connection that stops delivering, such as a half-open one, is found by a probe every 30 seconds and a short TCP keepalive, and replaced. `atomic storage status` says which applies ([#5103](https://github.com/bastani-inc/atomic/issues/5103))

### Changed

- A transaction's statements now go to the server without waiting for the answer to the one before, and a transaction that sends several before it commits takes one round trip for all of them and its commit ([#5102](https://github.com/bastani-inc/atomic/issues/5102))

### Fixed

- Atomic's tables now live in a schema of their own, `atomic` (the new `schema` option), set per transaction with `SET LOCAL search_path` so a transaction-mode pooler can serve it. The owner role creates it, so `CREATE DATABASE … OWNER <role>` is enough on Azure, Amazon RDS, Cloud SQL and PostgreSQL 15 and later, where `public` gives no one `CREATE`. A database whose `public` schema holds an earlier release's tables keeps using it until `atomic storage migrate` moves them. Advisory locks and `LISTEN` channels are scoped to the schema, unchanged in `public` ([#5218](https://github.com/bastani-inc/atomic/issues/5218))
- A statement refused for a missing privilege (`42501`) now fails with `StorageConfigError` reason `missing-privilege`, which names the privilege and the fix (the runtime role's grant, or `atomic storage migrate` as the owner role), instead of the server's bare message ([#5218](https://github.com/bastani-inc/atomic/issues/5218))
- A server certificate that TLS verification refuses (`ERR_TLS_CERT_ALTNAME_INVALID`, `UNABLE_TO_VERIFY_LEAF_SIGNATURE` and the like) is no longer retried five times as an unreachable server: the open fails at once with the reason and the fix, a host name the certificate names or `sslrootcert` ([#5218](https://github.com/bastani-inc/atomic/issues/5218))
- A cloud token the server refuses (`28P01`, or Azure's `28000` for a malformed one) is dropped and a fresh one tried once, so a clock that runs behind no longer reuses an expired Entra token for every new connection ([#5218](https://github.com/bastani-inc/atomic/issues/5218))
- `@azure/identity`, `@aws-sdk/rds-signer` and `google-auth-library` installed with `atomic install npm:<package>` are now found by an adapter installed from a local path, from the user packages in `~/.atomic/agent/npm`, not only beside the adapter ([#5218](https://github.com/bastani-inc/atomic/issues/5218))
- A value over PostgreSQL's limit (`54000`, program limit exceeded) now fails with `StoragePayloadTooLargeError`, which names the 1 GB field limit, instead of being reported as the store being unavailable ([#4954](https://github.com/bastani-inc/atomic/issues/4954))
- A `?` inside a dollar-quoted string whose tag contains a non-ASCII character that is not a letter, such as `$·$` or an emoji, is no longer treated as a parameter, so the parameters after it are numbered correctly. Identifiers containing such characters are recognised the same way, matching PostgreSQL. A `?` written directly after an identifier or keyword, as in `LIMIT?`, now becomes a separate parameter instead of being read as part of that name ([#4834](https://github.com/bastani-inc/atomic/issues/4834))
- `statementTimeoutMs` now applies to statements run outside a transaction too. Before, only the client gave up on such a statement, 5 seconds after the timeout, while the server kept running it, so a write reported as failed with an unknown outcome could still be saved afterwards. The server now cancels it at the timeout and the call fails as `transaction-timeout` with nothing written, also through a transaction-mode pooler. When the client does give up on a server or network that stopped answering, it also asks the server to cancel the statement ([#4901](https://github.com/bastani-inc/atomic/issues/4901))
- An identifier longer than PostgreSQL's 63 bytes, in any statement, now reaches the server as the storage dialect's name for it (its head and a hash of the whole name) instead of being truncated, so a store whose prefix makes its names long finds again every table, index and trigger it created ([#4793](https://github.com/bastani-inc/atomic/issues/4793))
- `sslmode` now follows libpq without extra parameters: `verify-ca` checks the server certificate's CA (`sslrootcert`, or the CAs Node.js trusts) but not its host name, so a server reached by an address its certificate does not name, such as Cloud SQL by private IP, connects instead of failing with "Hostname/IP does not match certificate's altnames". `require` with `sslrootcert` does the same. `prefer` and `allow` encrypt without checking the certificate. `require` without `sslrootcert` still checks the certificate and its host name, stricter than libpq, and a URL with `uselibpqcompat` keeps pg's own reading of `sslmode`. A TLS parameter whose name is not lowercase, such as `SSLMODE=verify-full`, is now refused instead of being ignored by pg, which connected to a remote host without TLS; an `sslmode` libpq does not know is refused too ([#5113](https://github.com/bastani-inc/atomic/issues/5113))

Their polls stay, so a dropped listening connection or a transaction pooler only makes them slower, never loses work. Through a transaction pooler, set the new `listenUrl` option to the server's direct endpoint; otherwise the adapter detects that notifications do not arrive, unlistens, and uses polling alone for the rest of the process, so it leaves no `LISTEN` on the pooler's server connections. A listening connection that stops delivering, such as a half-open one, is found by a probe every 30 seconds and a short TCP keepalive, and replaced. `atomic storage status` says which applies ([#5103](https://github.com/bastani-inc/atomic/issues/5103))

### Fixed

- Atomic's tables now live in a schema of their own, `atomic` (the new `schema` option), set per transaction with `SET LOCAL search_path` so a transaction-mode pooler can serve it. The owner role creates it, so `CREATE DATABASE … OWNER <role>` is enough on Azure, Amazon RDS, Cloud SQL and PostgreSQL 15 and later, where `public` gives no one `CREATE`. A database whose `public` schema holds an earlier release's tables keeps using it until `atomic storage migrate` moves them. Advisory locks and `LISTEN` channels are scoped to the schema, unchanged in `public` ([#5218](https://github.com/bastani-inc/atomic/issues/5218))
- A statement refused for a missing privilege (`42501`) now fails with `StorageConfigError` reason `missing-privilege`, which names the privilege and the fix (the runtime role's grant, or `atomic storage migrate` as the owner role), instead of the server's bare message ([#5218](https://github.com/bastani-inc/atomic/issues/5218))
- A server certificate that TLS verification refuses (`ERR_TLS_CERT_ALTNAME_INVALID`, `UNABLE_TO_VERIFY_LEAF_SIGNATURE` and the like) is no longer retried five times as an unreachable server: the open fails at once with the reason and the fix, a host name the certificate names or `sslrootcert` ([#5218](https://github.com/bastani-inc/atomic/issues/5218))
- A cloud token the server refuses (`28P01`, or Azure's `28000` for a malformed one) is dropped and a fresh one tried once, so a clock that runs behind no longer reuses an expired Entra token for every new connection ([#5218](https://github.com/bastani-inc/atomic/issues/5218))
- `@azure/identity`, `@aws-sdk/rds-signer` and `google-auth-library` installed with `atomic install npm:<package>` are now found by an adapter installed from a local path, from the user packages in `~/.atomic/agent/npm`, not only beside the adapter ([#5218](https://github.com/bastani-inc/atomic/issues/5218))
- A value over PostgreSQL's limit (`54000`, program limit exceeded) now fails with `StoragePayloadTooLargeError`, which names the 1 GB field limit, instead of being reported as the store being unavailable ([#4954](https://github.com/bastani-inc/atomic/issues/4954))
- A `?` inside a dollar-quoted string whose tag contains a non-ASCII character that is not a letter, such as `$·$` or an emoji, is no longer treated as a parameter, so the parameters after it are numbered correctly. Identifiers containing such characters are recognised the same way, matching PostgreSQL. A `?` written directly after an identifier or keyword, as in `LIMIT?`, now becomes a separate parameter instead of being read as part of that name ([#4834](https://github.com/bastani-inc/atomic/issues/4834))
- `statementTimeoutMs` now applies to statements run outside a transaction too. Before, only the client gave up on such a statement, 5 seconds after the timeout, while the server kept running it, so a write reported as failed with an unknown outcome could still be saved afterwards. The server now cancels it at the timeout and the call fails as `transaction-timeout` with nothing written, also through a transaction-mode pooler. When the client does give up on a server or network that stopped answering, it also asks the server to cancel the statement ([#4901](https://github.com/bastani-inc/atomic/issues/4901))
- An identifier longer than PostgreSQL's 63 bytes, in any statement, now reaches the server as the storage dialect's name for it (its head and a hash of the whole name) instead of being truncated, so a store whose prefix makes its names long finds again every table, index and trigger it created ([#4793](https://github.com/bastani-inc/atomic/issues/4793))
- `sslmode` now follows libpq without extra parameters: `verify-ca` checks the server certificate's CA (`sslrootcert`, or the CAs Node.js trusts) but not its host name, so a server reached by an address its certificate does not name, such as Cloud SQL by private IP, connects instead of failing with "Hostname/IP does not match certificate's altnames". `require` with `sslrootcert` does the same. `prefer` and `allow` encrypt without checking the certificate. `require` without `sslrootcert` still checks the certificate and its host name, stricter than libpq, and a URL with `uselibpqcompat` keeps pg's own reading of `sslmode`. A TLS parameter whose name is not lowercase, such as `SSLMODE=verify-full`, is now refused instead of being ignored by pg, which connected to a remote host without TLS; an `sslmode` libpq does not know is refused too ([#5113](https://github.com/bastani-inc/atomic/issues/5113))

### Changed

- A transaction's statements now go to the server without waiting for the answer to the one before, and a transaction that sends several before it commits takes one round trip for all of them and its commit ([#5102](https://github.com/bastani-inc/atomic/issues/5102))
