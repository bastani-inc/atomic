## [0.10.4] - 2026-11-22

### Fixed

- A call to a libSQL server (`sqld` or Turso) that waited on the server's write lock before receiving `SQLITE_BUSY` or `SQLITE_SCHEMA` (for example when another client's abandoned write timed out into a WAL checkpoint) now retries instead of failing at once. Retries use up to 5 seconds of jittered backoff and stop within at most 10 seconds from the start of the call, keeping fast refusals within about 5 seconds and stopping repeated slow-lock refusals after two attempts ([#6422](https://github.com/bastani-inc/atomic/pull/6422)).

## [0.9.90] - 2026-11-19

### Fixed

- A `CREATE TRIGGER` sent alone in `exec` now retries after `SQLITE_SCHEMA` while other connections change a libSQL server's schema. Semicolons inside the trigger body no longer make it look like several statements. An `exec` containing additional statements is still never replayed, also when names in the trigger use characters outside ASCII such as combining accents. One statement followed by white space outside ASCII after its `;`, such as a byte-order mark or a no-break space, counts as one statement again: it runs again after `SQLITE_SCHEMA` or a busy answer, falls back to a write transaction of its own while other connections keep changing the schema, and a `SELECT` written so runs on the reused stream, as before that trigger change ([#5509](https://github.com/bastani-inc/atomic/issues/5509), [#5676](https://github.com/bastani-inc/atomic/issues/5676))
- Write batches now refresh their schema after taking the write lock. A connection opened before another connection's schema change could otherwise report `no such table` for an existing table, including when a single write retried after `SQLITE_SCHEMA` ([#5536](https://github.com/bastani-inc/atomic/issues/5536))
- On a libSQL server (sqld) whose schema other connections keep changing, an `exec` of several statements outside a transaction no longer fails now and then with `SQLITE_SCHEMA: database schema has changed`, or with `SQLITE_BUSY`. The server refuses one statement this way without running it, after the statements before it committed, and the adapter used to report the failure without saying which statements ran. Such an `exec` is now sent as its statements, still in one request that runs them in order and stops at the first failure. A statement the server refused this way is sent again on its own, the way a single statement is, and the statements after it follow in another request. A statement that ran is never sent again. If a later request fails before reaching the server, the error is a `StorageTransientError` with an `unknown` outcome rather than `not-applied`, so the whole `exec` is not run again. A text with a `PRAGMA`, transaction control, a temporary table, a statement that returns rows (`SELECT`, `VALUES`, `WITH` or `RETURNING`), `last_insert_rowid()`, `changes()` or a parameter, or one the adapter cannot split exactly, is still sent as one text and not sent again. A text the server cannot read fails with the server's error for the whole text, which names the line and column in it, and an error inside a statement gives the same position as before ([#5652](https://github.com/bastani-inc/atomic/issues/5652))

## [0.9.89] - 2026-11-18

### Fixed

- A write that follows an outage on a libSQL server (sqld) or Turso database no longer waits for the adapter's next timed resend of the close of a stream the outage cut while it held the write lock. The adapter sent such a close again only on its backoff timer, 250 ms and then twice as long each time, so an outage longer than a wait left the close for the next one, up to seconds after the server was back, while the next write waited on the server for the lock the stream still held. Now every request sends the kept closes ahead of itself. A write waits for them, so that on a server that answers them the close arrives first and frees the lock; a request made only of plain `SELECT` statements does not wait, and any other statement, including `WITH`, `PRAGMA` and `EXPLAIN` queries, is treated as a possible write and may share the same bounded wait. Writes wait at most 2 seconds in all for closes the server takes but does not answer, then go ahead and wait for those closes no more, though a close kept later is waited for again; a caller's abort ends the wait at once. A close the server refuses because the outage lost the answer to a request it had already run still frees nothing: the lock clears when the server expires the stream. The timer still sends the closes while the database sends nothing else, and only its own unanswered resends lengthen its wait, once each. Against sqld after a 300 ms outage, the next write committed 4–14 ms after the server was back instead of 455–466 ms ([#5114](https://github.com/bastani-inc/atomic/issues/5114)).
- Fixed a worker host crashing after a libSQL server rolled back a write batch. Batch execution now observes every statement, COMMIT and ROLLBACK result, so later timeout rejections cannot escape the reported storage failure. A batch whose COMMIT never ran is no longer reported as successful ([#4768](https://github.com/bastani-inc/atomic/issues/4768))
- Fixed `run`, `get` and `all` statements failing with `Storage unavailable` on `ws:` and `wss:` URLs. These statements now use WebSockets instead of attempting HTTP requests ([#4768](https://github.com/bastani-inc/atomic/issues/4768))
- On a libSQL server (sqld) shared by stores that create and drop their tables, such as several sessions, workflows or teams using one server, a statement no longer fails with `SQLITE_SCHEMA: database schema has changed` when other connections change the schema while the server prepares it. The server ran nothing of such a statement, so it is sent again, as a statement the server answers busy is, for up to 5 seconds. A write outside a transaction (`INSERT`, `UPDATE`, `DELETE`, `REPLACE`, or a `WITH` that writes), or a schema change (`CREATE`, `DROP`, `ALTER`) sent alone in one `exec`, also no longer fails with `SQLITE_SCHEMA` while other connections keep changing the schema for longer than the 5-second wait. Sent again as it was, such a write could meet a changed schema on every try, and on a loaded server only two or three tries fit in the wait. After the first `SQLITE_SCHEMA` answer, such a statement is now sent again inside a write transaction of its own, in one request, with a wait of its own. While the transaction holds the write lock no other connection can change the schema, so the statement runs, and it commits once or not at all. Reads (including `VALUES` and a `WITH` that only selects) and other statements, such as pragmas, are still sent again as they were. A statement inside a transaction, and several statements sent in one `exec`, are not sent again
- On a libSQL server (sqld) shared by stores that create and drop their tables, a read or write outside a transaction no longer fails now and then with `SQLITE_UNKNOWN: no such table` for a table that exists. sqld gives that answer, without running the statement, when it compiles the statement while other connections change the schema; it happened to a `DELETE` from a table whose rows a trigger also removes from a full-text index, on kept and new streams alike. When the server names a table the database's schema lists, the statement now runs again with growing waits, up to 20 times; a table that does not exist is still reported at once ([#5464](https://github.com/bastani-inc/atomic/issues/5464))

## [0.9.88] - 2026-11-16

### Changed

- Statements outside a transaction on a libSQL server (sqld) or Turso database now reuse one Hrana stream instead of opening a new one for every request ([#5151](https://github.com/bastani-inc/atomic/issues/5151)). sqld loads the database's schema for every stream it opens, so the server's work for each request grew with the number of tables: on one sqld, a pooled workflow round used 6.0 s of server CPU with no other tables, 8.3 s with 100 and 13.1 s with 400; it now uses 2.9, 3.2 and 3.8 s. Only reads and writes (`SELECT`, `INSERT`, `UPDATE`, `DELETE`, `REPLACE`, `WITH`, `VALUES`) reuse the stream; schema changes, pragmas, transaction control, transactions and write batches keep a stream of their own, so a reused stream never holds a transaction or the write lock. A stream idle 5 seconds or open 60 seconds is closed and a new one opened, before sqld would expire it. A statement is sent again only when the server refused it without running it, because the stream had expired or its baton was refused before anything ran; a statement whose answer was lost, or any other refusal, is not, and the next statement opens a new stream. Each statement on a kept stream is preceded, in the same request, by a read of `sqlite_schema`, so the stream's connection rereads a schema another process changed: without it, a kept connection compiled the next statement against the old schema, and `SELECT *` returned the old columns. A stream's first request that fails no longer sends the server a close for a stream it never opened.

### Fixed

- A libSQL server (sqld) or Turso database no longer stays locked for the stream's whole lifetime after an outage that cut a stream holding a write transaction. The client sends the close of a stream it gives up on once, and in an outage that close failed too, so the server kept the stream, its open transaction and the database's write lock: every writer, in this process and every other, waited for it, and a worker host could stay stuck for over a minute after the database came back. The adapter now sends such a close again, waiting 250 ms and then twice as long each time up to 8 s, until the server answers it, for at most 5 minutes, and stops when the database closes; a close that reaches the server frees the lock at once. When the outage lost the answer to a request the server had already run, the server refuses the close as a used baton, the adapter does not send it again, and the lock clears when the server expires the stream, about 5 seconds on sqld ([#5114](https://github.com/bastani-inc/atomic/issues/5114)).
- An HTTP 5xx answer with no libSQL error in it, such as a gateway's 502 or 504 in front of sqld or Turso, is now a `StorageTransientError` with code `connection-lost`. Its outcome is `"unknown"` for a commit, a batch or a statement outside a transaction, because the server may have applied the request before the answer was lost. Before, it was a plain `StorageUnavailableError`, and a session save the server had applied counted as failed ([#4970](https://github.com/bastani-inc/atomic/issues/4970)).
- A value over a libSQL server's limit (`SQLITE_TOOBIG`, or `ARGS_INVALID: string or blob too big`; 5,000,000 bytes by default in sqld) and a response over its 10 MB limit (`RESPONSE_TOO_LARGE`) are no longer reported as `StorageUnavailableError`. They fail with `StoragePayloadTooLargeError`, which names the size and sqld's default limit and is never retried. Atomic's sessions and snapshots now store large values in rows of at most 1 MiB, so they stay under these limits ([#4954](https://github.com/bastani-inc/atomic/issues/4954))
- A libSQL server (sqld) database no longer fails a write with `SQLITE_BUSY: database is locked` when the write meets the server's checkpoint. sqld answers such a write `SQLITE_BUSY` at once, without running any of it, and leaves the waiting to the client, so a write that coincided with a checkpoint failed with `StorageUnavailableError`. A statement outside a transaction, an `exec` of one statement, a batch, or the start of a transaction that the server answers busy now runs again with growing waits for up to 5 seconds. A statement the server answers busy after its transaction began, and several statements in one `exec`, do not run again ([#4817](https://github.com/bastani-inc/atomic/issues/4817)).
- Closing a `file:` database no longer crashes the process on Windows. `libsql` 0.5.29, the native driver `@libsql/client` uses, closes a local connection's SQLite handle twice when the connection holds its last reference ([tursodatabase/libsql#2251](https://github.com/tursodatabase/libsql/issues/2251)). The second close reads freed memory, and Windows ends the process with `0xC0000005` and no message. A process with several connections open took that path on the close after its first, because each close's garbage collections finalized the other connections' statements. The adapter now closes each local connection while a statement still holds it, so the handle closes once. A `libsql` release built with the crate fix ([tursodatabase/libsql#2261](https://github.com/tursodatabase/libsql/pull/2261)) makes this unnecessary ([#4824](https://github.com/bastani-inc/atomic/issues/4824)).
- Fixed many processes writing to one sqld or Turso database stalling each other ([#4768](https://github.com/bastani-inc/atomic/issues/4768)). A write batch that finds the server's write lock busy is now sent again after a short random wait that grows up to a second, for as long as the caller's `lockWaitMs` allows. Each process sends at most four write batches to a server at once; a batch with `priority` skips that limit. A request the server leaves unanswered for 30 seconds is abandoned, as a transient failure whose outcome is unknown, instead of waiting for the network's own timeout. Three write requests in a row left unanswered print a warning (`ATOMIC_LIBSQL_WRITES_STALLED`) naming [tursodatabase/libsql#2286](https://github.com/tursodatabase/libsql/issues/2286), a sqld bug that stops it taking writes until it restarts, and its workaround: start sqld with `--checkpoint-interval-s 60`. The first write answered afterwards prints `ATOMIC_LIBSQL_WRITES_RECOVERED`
- A libSQL server that stops answering writes no longer holds back writes to another server from the same process. The limit of four write batches in flight now applies to each server separately, so writes to a healthy server, and the calls queued behind them on that database, go on while another server is stalled ([#4790](https://github.com/bastani-inc/atomic/issues/4790))
- A statement whose leading comments a regular expression could split many ways, such as `/**//**//**/… PRAGMA …`, no longer stalls the process deciding whether it may reuse the open stream. That check used to backtrack exponentially in the number of comments; it now reads the statement once, and it ends a block comment at its first `*/`, as SQLite does.

## [0.9.75] - 2026-11-10

### Fixed

- A `file:` database no longer fails a write with `SQLITE_BUSY: database is locked` while other processes keep committing to the file. SQLite's busy handler polls for the lock with growing sleeps, so a writer behind others that took the lock in turn could miss every poll and fail after the 5-second busy timeout although the lock changed hands hundreds of times meanwhile. A statement outside a transaction, an `exec` of one statement such as a `CREATE TABLE IF NOT EXISTS`, a batch, or the start of a transaction that waited out the busy timeout now runs again, on new connections, as long as another connection committed during its wait; it fails only after a whole busy timeout in which nobody committed. Several statements in one `exec` do not run again.

## [0.9.72] - 2026-11-08

### Fixed

- A `file:` database stays usable after a statement fails. A statement that gave up part way, for example a write that waited out the busy timeout while another process held the lock, stayed active on its connection until garbage collection. After that, every transaction on the database failed with `SQLITE_BUSY: cannot commit transaction - SQL statements in progress`, and a write outside a transaction reported success but was never committed. The adapter now replaces its local connections after any failed statement, before the next call, and turns foreign keys on again on the new one.
- Closing a `file:` database now releases its files before `close()` resolves, so they can be deleted or moved right away, including on Windows. libsql 0.5 keeps a closed connection open until its statements are garbage-collected; the adapter now runs two full garbage collections, shared by closes that arrive together, and waits for the driver to release its handles ([#4433](https://github.com/bastani-inc/atomic/issues/4433))
- When opening a database fails and closing it afterwards fails too, the close failure is attached to the open error as `cleanupCause` instead of being discarded ([#4433](https://github.com/bastani-inc/atomic/issues/4433))
- A remote database no longer fails a write because the process stalled in the middle of it. When a process was stopped (by a signal, starved of CPU, or asleep) longer than the server keeps an idle stream, its next statement failed with `STREAM_EXPIRED` and the write was lost to a `StorageUnavailableError`. The adapter now recognizes an expired stream, a transaction the server timed out, a refused connection and a broken connection by their codes and reports them as `StorageTransientError`; a statement, batch, or workflow journal or session write that they ended before it wrote anything runs again, up to five times over about four seconds. A write whose connection broke after the server may have applied it is not sent again and fails with `outcome: "unknown"` ([#4383](https://github.com/bastani-inc/atomic/issues/4383))
