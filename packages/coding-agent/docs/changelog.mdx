<Update label="November 26, 2026" description="0.10.11-alpha.2">

Forks in a SQLite, libSQL or PostgreSQL session store now read their parent's history instead of copying it, and session and Intercom stores make fewer round trips.

**Breaking change:** Once no older Atomic has a session open on a session database, Atomic upgrades it so that forks share their parent's history. Older Atomic versions then stop opening that database with "this store needs a newer Atomic". Upgrade every machine and CI job that shares a database. On PostgreSQL, a role that cannot create tables keeps copying forks until the owner runs `atomic storage migrate`. To take sessions back to an older version, export them with `atomic storage export` and import them with that version into a new store ([#6600](https://github.com/bastani-inc/atomic/pull/6600), [#6614](https://github.com/bastani-inc/atomic/pull/6614)).

**Forks**

- **A fork costs the same as a new session.** `/fork`, `/clone`, `atomic --fork` and forked subagents store only where the fork starts and read the parent's entries from the parent. Creating a fork takes the same round trips as creating a session, whatever the parent's length or how many forks deep it is. A subagent fork of a 500-entry session takes 8 round trips instead of 1,012 on PostgreSQL and on a libSQL server, and 12 instead of 1,018 on SQLite. 50 forks at once on PostgreSQL finish in 119 ms instead of 2.6 s. The store no longer holds a second copy of the parent's history. A fork lists, searches, resumes and keeps worktree snapshots as a copy does, and later changes to the parent never show up in it ([#6602](https://github.com/bastani-inc/atomic/pull/6602), [#6608](https://github.com/bastani-inc/atomic/pull/6608), [#6601](https://github.com/bastani-inc/atomic/pull/6601), [#6614](https://github.com/bastani-inc/atomic/pull/6614)).
- **Deleting a parent keeps its forks whole.** A deleted session leaves every list and search at once. The store keeps the entries its forks read until the last of those forks is deleted. Rewriting a parent first gives each fork its own copy ([#6598](https://github.com/bastani-inc/atomic/pull/6598)).
- **Exports stay standalone.** `atomic storage export`, `/export`, `/share`, HTML export and moving sessions to another store write each fork's full history, so the copy needs none of the sessions it came from ([#6598](https://github.com/bastani-inc/atomic/pull/6598)).

**Faster stores**

- **Faster PostgreSQL store opens.** Opening a session store whose tables are up to date takes 2 round trips instead of 5, and an Intercom broker takes 1 instead of 3. At 80 ms latency, reopening a session store takes about a quarter of a second less ([#6606](https://github.com/bastani-inc/atomic/pull/6606)).
- **One round trip per save on PostgreSQL.** After you run `atomic storage migrate` as the owner role, saving new entries to a session takes 1 round trip instead of 2, because a database function does the whole save. At 80 ms latency the median save took 108 ms instead of 193 ms. Older Atomic releases keep working on a database that has the function ([#6604](https://github.com/bastani-inc/atomic/pull/6604)).
- **Prepared statements behind PgBouncer.** Atomic now keeps statements prepared behind PgBouncer 1.21 or later when its `max_prepared_statements` is above 0, which is the default from 1.24, so the server parses each statement once. It finds this out on its first connection with no extra round trip. Behind other poolers they stay off, and a `maxPreparedStatements` you set still wins ([#6604](https://github.com/bastani-inc/atomic/pull/6604)).
- **Faster `history://` searches.** A search of a past session that Atomic has indexed reads the matching entries, and the lines shown around them, in one request instead of one request per entry. At 80 ms latency a search with 8 matches took 0.5 s instead of 2.8 s on PostgreSQL, and 0.5 s instead of 2.9 s on a libSQL server. A larger benchmark search took 9 round trips instead of 97. A custom `SessionStore` receives the entries to read in the new `seqs` field of `readEntryRange` ([#6607](https://github.com/bastani-inc/atomic/pull/6607)).
- **libSQL reads share requests.** On a libSQL server, single reads made at the same time go out together in one request. With 8 reads at once, the server got 2 requests instead of 8, and the first burst opened no new connection instead of 5 ([#6607](https://github.com/bastani-inc/atomic/pull/6607)).
- **No write lock to reopen a broker on SQLite and libSQL.** Reopening an Intercom broker whose tables are set up no longer takes the database's write lock, so brokers that start together no longer wait for each other. On a libSQL server 80 ms away, a reopen takes 0.4 s instead of 0.6 s. A process's first chat record skips the lock the same way. If anything changes the tables later, including an older Atomic, the next open checks them again ([#6609](https://github.com/bastani-inc/atomic/pull/6609)).
- **Faster writes to libSQL files.** On a local libSQL `file:` database, each connection keeps up to 256 prepared statements and reuses them. Saving a new 500-entry session takes 6.3 ms instead of 66 ms, and saving one entry about 0.2 ms instead of 0.4 ms ([#6613](https://github.com/bastani-inc/atomic/pull/6613)).
- **Faster local SQLite reads.** Reading a session's latest entries or resuming it from a local SQLite file waits for the database's background thread 2 or 3 times instead of 4 or 5 ([#6609](https://github.com/bastani-inc/atomic/pull/6609)).
- **Faster JSONL sessions.** On macOS and Linux, Atomic keeps a session's JSONL file open while it writes, and puts entries saved at the same moment into one write. Saving an entry takes 7 file operations instead of 18, and ten saves at once take 7 instead of 180. A folder of 201 sessions reopens in about 9 ms instead of about 640 ms ([#6605](https://github.com/bastani-inc/atomic/pull/6605)).

**Intercom**

- **Brokers pick up waiting messages faster.** With multi-node routing, taking a session's waiting messages takes 1 round trip instead of 3 on PostgreSQL, about 100 ms instead of 280 ms at 80 ms latency. On a libSQL server it takes 2 round trips instead of 3, and on a SQLite file 2 calls instead of 5 to 9 ([#6610](https://github.com/bastani-inc/atomic/pull/6610), [#6615](https://github.com/bastani-inc/atomic/pull/6615)).
- **Intercom records deliveries together.** With multi-node routing on PostgreSQL, messages that recipients confirm at about the same time are recorded as delivered in one transaction of 2 round trips, instead of 2 round trips for each message. At 80 ms latency, four confirmations took 0.19 s instead of 0.55 s and opened no extra database connections ([#6606](https://github.com/bastani-inc/atomic/pull/6606)).

**Fixes**

- **No `Storage unavailable` errors under load on a libSQL server.** Atomic now closes a database's idle connection to the server after 5 seconds, and sends a request again when the server turns it away as busy. In a test with 100 agents writing at once, 1 run in 6 failed before and none of 8 after ([#6616](https://github.com/bastani-inc/atomic/pull/6616)).
- **Forks copy only the pieces each long entry uses.** Forking a session that holds leftover pieces of long entries, which an older Atomic can leave behind, no longer copies them into the fork or fails with `Missing chunk of session entry` ([#6611](https://github.com/bastani-inc/atomic/pull/6611)).
- **Intercom keeps one session's messages in order on PostgreSQL.** When a broker was slow to renew its hold on an earlier message, another broker could take that message over while the first delivered a later one. Brokers now take turns on one session's messages ([#6610](https://github.com/bastani-inc/atomic/pull/6610)).

</Update>

<Update label="November 25, 2026" description="0.10.11-alpha.1">

Many agents can now share one PostgreSQL or libSQL database without waiting for each other, forks cost about the same however long the session is, and shell commands and history searches now run until they finish.

**Breaking change:** Atomic and its npm packages now need Node.js 24.20.0 or newer. Run `node --version`. If it is older, install the current Node.js 24 LTS release from [nodejs.org](https://nodejs.org/en/download) or with `nvm install 24`, `fnm install 24` or `mise use -g node@24`, then reinstall Atomic with `npm install -g @bastani/atomic`. If you installed with `install.sh` or `install.ps1`, you need no change, because those installs bring their own runtime. Node.js releases before 24.15.0 bundle a SQLite bug that can corrupt the session database, and 24.17.0 through 24.19.0 reject valid certificates for IPv6 addresses ([#6579](https://github.com/bastani-inc/atomic/pull/6579)).

**Shared databases**

- **Agents on one PostgreSQL database stop queueing.** A session save now locks only its own session and takes 2 round trips instead of 7 or more. In a load test with 100 agents at 80 ms latency, a save took 164 ms instead of 52 to 57 seconds, and 200 agents ran without lock timeouts. Run `atomic storage migrate` once before you start many agents ([#6588](https://github.com/bastani-inc/atomic/pull/6588), [#6560](https://github.com/bastani-inc/atomic/issues/6560)).
- **Faster startup.** On PostgreSQL, opening a session store whose tables are up to date takes 5 round trips instead of 43 and takes no lock. On SQLite and libSQL it reads the schema in one statement: reopening an Intercom broker on a libSQL server 80 ms away takes 0.6 s instead of more than 6 s, and on a local SQLite file it takes 1 write lock instead of 30 ([#6588](https://github.com/bastani-inc/atomic/pull/6588), [#6599](https://github.com/bastani-inc/atomic/pull/6599)).
- **Forks no longer copy entry by entry.** A fork within one database is copied by the database in a few statements, so its cost barely grows with the session's length. At 80 ms latency, a subagent fork of a 500-entry session takes 1.2 s instead of 17.8 s, and a clone 2.6 s instead of 33 s. Two handles on the same database count as one store. Forks from another store read it in larger requests and no longer wait for each other ([#6596](https://github.com/bastani-inc/atomic/pull/6596), [#6591](https://github.com/bastani-inc/atomic/pull/6591)).
- **Faster reads and snapshots.** Reading a session's latest entries or resuming it takes 2 round trips instead of 5 or 6 on PostgreSQL, and about half the time on libSQL. Back-to-back reads reuse one PostgreSQL connection. Storing five snapshot blobs takes 172 ms instead of 585 ms ([#6599](https://github.com/bastani-inc/atomic/pull/6599), [#6588](https://github.com/bastani-inc/atomic/pull/6588)).
- **Fewer PostgreSQL connections.** Every store a process opens on the same database shares one connection pool, and reads use their own pool of up to 2 connections. The new `readerMaxConnections`, `maxPreparedStatements`, `connectTimeoutMs`, `idleTimeoutMs` and `keepAliveIdleMs` options tune them. New guides cover [PostgreSQL tuning for many agents](https://docs.bastani.ai/guides/postgres-tuning) and [PgBouncer](https://docs.bastani.ai/guides/postgres-pgbouncer) ([#6588](https://github.com/bastani-inc/atomic/pull/6588)).
- **`atomic storage migrate` sets up every table.** It now creates the chat-record table and Intercom's queue for ended subagents, so a database role that cannot create tables keeps turn diagnostics and messages for ended subagents. It also leaves free space on the busiest tables' pages, so frequent row updates stay cheap ([#6588](https://github.com/bastani-inc/atomic/pull/6588)).
- **Faster SQLite and libSQL.** Local SQLite reuses up to 256 prepared statements per connection. On a libSQL server, reads made at once run at the same time, up to the new `concurrency` option (20 by default), and a transaction takes 2 requests instead of 6. The new `keepAliveMs` option keeps idle connections to a self-hosted libSQL server open ([#6588](https://github.com/bastani-inc/atomic/pull/6588)).
- **Intercom across hosts stops waiting.** With multi-node routing on PostgreSQL, sends to different sessions no longer wait for each other: with 50 brokers sending at once, the median send took 0.27 seconds instead of 12. A broker starts in about 3 round trips instead of about 100, checks for messages less often while database notifications work, and `intercom list` shows other hosts' sessions while writes are busy ([#6588](https://github.com/bastani-inc/atomic/pull/6588)).
- **Storage SDK additions.** `SqliteDatabase.openReader()` returns a read handle with its own connection on SQLite files, libSQL and PostgreSQL. `@bastani/atomic/storage` exports `withStorageSchemaCatalog`, `schemaCatalogOf`, `storageSchemaCurrent`, `ensureTableFillfactor` and `transactionFinisher`, so your own stores can use the same schema check and pipelined commits ([#6588](https://github.com/bastani-inc/atomic/pull/6588)).

**Long-running work**

- **Shell commands have no default time limit.** `bash` and `powershell` commands no longer stop after 5 minutes. Builds, test runs, dev servers and watchers run until they finish or you stop them with `kill` or `/tasks`. `timeout` still sets a deadline, now with no upper limit. A session runs at most 64 commands at once ([#6574](https://github.com/bastani-inc/atomic/pull/6574), [#6581](https://github.com/bastani-inc/atomic/pull/6581)).
- **Slow `history://` reads and searches keep running.** They no longer stop after 3 seconds. After 10 seconds the agent gets a task ID and keeps working, and the result arrives when it is ready ([#6563](https://github.com/bastani-inc/atomic/pull/6563)).

**Skills and subagents**

- **Skills listed by `skill://` address.** The model's instructions name each skill as `skill://<name>` instead of the full path to its `SKILL.md`, so your home folder no longer appears in every prompt and the addresses keep working after a skill moves or a session resumes on another computer. `read`, `search`, `find` and `bash` open these addresses, and a subagent given a skill gets its address too ([#6589](https://github.com/bastani-inc/atomic/pull/6589)).
- **Subagents always use the parent's session store.** A subagent saves its session where its parent does, whatever its folder, worktree or project settings, including after a restart. `sessionDir` and `defaultSessionDir` are ignored with a warning. Forked subagents are left out of `/resume`, like fresh ones ([#6594](https://github.com/bastani-inc/atomic/pull/6594)).
- **The agent panel remembers `main` and `/tasks` choices.** `↓` from an empty prompt returns to the row you chose last, including `main` and a subagent you opened from `/tasks`. `↓` on the last row moves to the first ([#6564](https://github.com/bastani-inc/atomic/pull/6564)).
- **Expanded subagent cards show the work.** Expanding a subagent that waits on a tool call shows its task and its tool calls, with the waited-on call marked `◌` ([#6562](https://github.com/bastani-inc/atomic/pull/6562)).
- **Clearer subagent model errors.** The error says whether the model does not exist or `enabledModels` leaves it out, and names the exact ID to add for a Fast or Ultrafast version ([#6569](https://github.com/bastani-inc/atomic/pull/6569)).

**Fixes**

- **macOS stops Atomic's commands when Atomic dies**, including background servers ([#5057](https://github.com/bastani-inc/atomic/issues/5057), [#6580](https://github.com/bastani-inc/atomic/pull/6580)).
- **Compaction network errors name the cause**, including DNS filters such as NextDNS, Pi-hole or AdGuard blocking the server ([#6561](https://github.com/bastani-inc/atomic/pull/6561)).
- **A default model after a provider retires one.** Atomic picks another model from that provider's catalog ([#6582](https://github.com/bastani-inc/atomic/pull/6582)).
- **Intercom starts with a long relative agent directory** on macOS and Linux ([#6585](https://github.com/bastani-inc/atomic/pull/6585)).
- **Backups of a custom agent directory stay separate** from the moved original's session store ([#5242](https://github.com/bastani-inc/atomic/issues/5242), [#6570](https://github.com/bastani-inc/atomic/pull/6570)).
- **Turso writes after a pause** no longer fail with `ECONNRESET` on Bun, including the `atomic` binary ([#6588](https://github.com/bastani-inc/atomic/pull/6588)).
- **Stall reports on macOS include stacks again** after the Mac has slept ([#6583](https://github.com/bastani-inc/atomic/pull/6583)).

</Update>

<Update label="November 23, 2026" description="0.10.5">

Atomic starts faster, installs fewer files, keeps subagents and Intercom messages intact across restarts, and makes Windows installs, process stops, and proxies more reliable.

**Startup and installs**

- **Faster warm starts.** Compared with 0.10.4, time to first prompt drops by about 100 ms on Linux (0.74 s to 0.64 s) and about 220 ms on Windows (1.32 s to 1.10 s on Windows Server 2022, 1.22 s to 1.00 s on Windows 11) ([#6455](https://github.com/bastani-inc/atomic/pull/6455))
- **Faster Windows cold starts.** In-process cold starts on Windows Server 2022 drop from 10.8 s to 3.5 s. Syntax-highlighter grammars now wait until after the first prompt dispatches and load in short slices instead of blocking the session ([#6444](https://github.com/bastani-inc/atomic/pull/6444))
- **Settings edits keep the prestarted engine.** Editing `debug` or `httpProxy` in `settings.json` during startup updates the prestarted engine instead of starting a second one. On Windows this cuts startup by 534 to 724 ms in npm installs and standalone binaries ([#6453](https://github.com/bastani-inc/atomic/pull/6453), [#6478](https://github.com/bastani-inc/atomic/pull/6478))
- **Smaller npm installs.** Dropping 13 already-bundled packages cuts global npm installs by 1,938 files and 10.8 MiB ([#6440](https://github.com/bastani-inc/atomic/pull/6440))
- **Windows installer retries file locks.** Reinstalling, repairing, or rolling back on Windows retries locked file moves and directory cleanups for up to 9.5 s instead of failing on antivirus or search-indexer locks ([#6474](https://github.com/bastani-inc/atomic/pull/6474))

- **Shared storage across machines:** install `@bastani/atomic-storage-libsql`, join a machine with `atomic storage join <url> --token-file <path>`, and check the result with `atomic storage status`. Atomic packages can ship their own storage adapters, and `createSqliteDatabase()` applies the facade rules when you write one ([#3856](https://github.com/bastani-inc/atomic/issues/3856), [#3857](https://github.com/bastani-inc/atomic/issues/3857))
- **Intercom you can inspect and restart:** `atomic intercom status` and `atomic intercom restart` show and refresh the broker's storage selection and multi-node routing, and a broker that stops answering is replaced after about a minute instead of hanging every session ([#3857](https://github.com/bastani-inc/atomic/issues/3857), [#3862](https://github.com/bastani-inc/atomic/issues/3862))
- **Rate limits handled across requests:** `configureProviderRequestBudget()` sets process-wide request budgets, 429 cooldowns are shared between model requests, and workflow model chains wait for the earliest eligible account instead of exhausting it ([#3864](https://github.com/bastani-inc/atomic/issues/3864))
- **Admission limits and local workflow pools:** SDK hosts can share session and command limits with `resourceAdmission`, and workflows can run child subtrees in local worker processes ([#3869](https://github.com/bastani-inc/atomic/issues/3869))
- **More responsive sessions and workflows:** Ctrl+C and queue clearing act without waiting for a busy engine, workflow stages reload resources four at a time, and standalone `run()` gives stages Intercom without an interactive host ([#3861](https://github.com/bastani-inc/atomic/issues/3861), [#3863](https://github.com/bastani-inc/atomic/issues/3863), [#3865](https://github.com/bastani-inc/atomic/issues/3865))
- **Login, export, and search fixes:** device-code `/login` waits for Enter before opening the browser, HTML exports show billed costs and the session's own system prompt, and `/resume` search ranks name matches first ([pi #9282](https://github.com/earendil-works/pi/issues/9282), [pi #9980](https://github.com/earendil-works/pi/issues/9980), [pi #11261](https://github.com/earendil-works/pi/issues/11261), [pi #11220](https://github.com/earendil-works/pi/issues/11220))
- **Security updates:** the standalone binaries embed Bun 1.4.4 with its upstream security fixes, and the bundled `ip-address` dependency no longer stalls on a long crafted IPv6 string ([GHSA-rxp7-6hxx-x8q5](https://github.com/advisories/GHSA-rxp7-6hxx-x8q5))

</Update>

<Update label="October 22, 2026" description="0.9.41">

Workflows stay contained when they fail, classifiers read images, and usage totals say where their cost came from.

- **Workflow failures stay inside their run:** an unhandled `ctx` rejection, a stray `ctx.exit()`, or a branch that outlives a kill or quit now fails or ends only its own run instead of the whole Atomic process ([#3846](https://github.com/bastani-inc/atomic/issues/3846), [#3849](https://github.com/bastani-inc/atomic/pull/3849))
- **Image input for more classifiers:** `models.classify()` accepts `images` for Jev and Clef on Cloudflare Workers AI and OpenRouter, with corrected Workers AI pricing ([#3847](https://github.com/bastani-inc/atomic/pull/3847))
- **Provider-billed cost flag:** `usage.cost.totalFromProvider` tells you whether a usage total is the provider's billed cost or a catalog estimate ([#3852](https://github.com/bastani-inc/atomic/pull/3852))
- **Steady sessions and installs:** SDK and RPC `steer()`/`followUp()` start a turn on an idle session, extension OAuth providers can report rejected logins, and the installers skip downloading a release that is already installed ([#3801](https://github.com/bastani-inc/atomic/issues/3801), [#3851](https://github.com/bastani-inc/atomic/pull/3851))
- **Terminal and rendering fixes:** Rex terminal support, terminal modes restored on unexpected exit, Markdown tables after unclosed `$$` blocks, CJK emphasis, and `@` autocomplete with regex characters ([#3847](https://github.com/bastani-inc/atomic/pull/3847))

**Breaking change:** SDK `steer()` and `followUp()` and the RPC `steer` and `follow_up` commands now start a turn when the agent is idle and the session already has messages.

</Update>
