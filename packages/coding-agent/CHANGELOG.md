# Changelog

## [Unreleased]

### Breaking Changes

- Removed automatic model routing. `model: "auto"` in subagents, agent files, workflow stages and the builtin workflows and agents now runs your default model (`defaultProvider`/`defaultModel`, the model you last chose with `/model`) at its `modelThinkingLevels` entry or `defaultThinkingLevel` unless the caller sets an effort, or the current session's model and thinking level when no default is configured or it has no credentials. No model is asked to choose, so an `auto` launch makes no routing request. `decisionModel`, `decide()`, `generateStructuredOutput()` and the `structured_output` tool are unchanged.
- Removed the `modelRouting` setting. Saved settings that still contain it load without an error, the key is dropped with a one-time warning (shown in the chat while the interactive UI is open), and its provider and model restrictions no longer limit `auto` or any fallback model; a legacy `routerModel` key still migrates to `decisionModel`.
- Removed the routing SDK exports `routeExecutionModel`, `AutoRoutingInferenceError`, `ModelRoute`, `ModelRoutingContext`, `RoutingInferenceBounds`, `ParallelSlot`, `ModelRouterOutput`, `ModelConstraints`, `ModelConstraintsSchema`, `parseModelConstraints`, `eligiblePair`, `setsProviders`, `TaskNeeds`, `TaskNeedsSchema`, `parseTaskNeeds`, `mergeTaskNeeds`, `WORK_KINDS`, `DIFFICULTY_LEVELS`, `MISTAKE_COST_LEVELS`, `WorkKind`, `Difficulty`, `MistakeCost`, `reportModelRoutingDebug` and `ModelRoutingSettings`, along with `SettingsManager.getModelRouting()`, `ExtensionContext.getModelRouting()`, the `routerSelection` field of the exported `AgentIntent` and `TaskRecord` types, and the `model-routing` debug area and its `ATOMIC_MODEL_ROUTING_DEBUG` variable. A decision classifier's fallback to the chat model is now recorded only in the debug log, under the new `decision` debug area.
- Removed the model benchmark docs (`models/evals` and `models/model-selection`) and the script that refreshed them. When asked which model to choose, the system prompt no longer sends the agent to benchmark docs or benchmark sites.
- On Windows, `ensurePrivateTempDir()` and `assertPrivateDirectory()` no longer read a directory's owner and access list on the main thread. They accept a directory already checked in the process; otherwise they start the check in the background, and `assertPrivateDirectory()` throws `TempDirRefusedError` ("its ownership is still being verified") while `ensurePrivateTempDir()` returns another private directory. **Migration:** use `ensurePrivateTempDirAsync()` and `assertPrivateDirectoryAsync()` on Windows to wait for the check ([#5285](https://github.com/bastani-inc/atomic/issues/5285))
- `Selector` single-select pickers now stop accepting input after `onSelect` by default, including Esc and Ctrl+C. For persistent or multi-stage pickers that call `setItems()` after a choice, pass `closeOnSelect: false`. If saving a choice fails, call `retrySelection()` to accept input again. `onConfirm` and `onCancel` still stop the picker ([#5224](https://github.com/bastani-inc/atomic/issues/5224))
- `SelectorState.items` is now read-only, and item-list snapshots are frozen. Replace `state.items = rows` and array mutations with `state.setItems(rows)`, or use `selector.setItems(rows)` for a rendered picker. Copy a snapshot before modifying it ([#5224](https://github.com/bastani-inc/atomic/issues/5224))

### Added

- Set `ATOMIC_EVENT_LOOP_BLOCK_MS` to a positive whole number of milliseconds to log every stall of the interactive UI or its engine at least that long, with the functions that were running and each process's event-loop delay for startup, the session and shutdown, to `event-loop-blocks.jsonl` in the agent directory or the file `ATOMIC_EVENT_LOOP_BLOCK_LOG` names. Nothing starts while it is unset. See [Finding what freezes the UI](/development#finding-what-freezes-the-ui)
- SDK: `BashToolOptions.commandPrefix` accepts a promise, awaited for each command, and asynchronous forms of helpers that used to block: `resolveInstalledGit`, `processSharedStorageSelectionAsync` and `processStorageEnvironmentAsync`
- SDK: `loadMcpConfigAsync`, `updateMcpServerConfigAsync`, `addMcpServerConfigAsync`, `removeMcpServerConfigAsync`, `savedProjectTrustAsync`, `latestSessionSnapshotAsync`, `mapPathForCwdAsync`, `AuthStorage.createAsync()`, `SettingsManager.createAsync()`, `ModelRuntime.getCompatibilityRequestConfigAsync()` and `ModelRuntime.getCatalogInputsGenerationAsync()`. Existing synchronous forms retain their return types
- SDK: `getProjectTrustOptionsAsync`, `hasProjectTrustInputsAsync`, `hasTrustRequiringProjectResourcesAsync`, `buildSkillCatalogAsync`, `emptySkillCatalog`, `mapRestoredPathAsync`, `workspaceSessionCwdAsync`, `takeTakeoverMutexAsync`, `appendDebugRecordAsync`, `reportDebugAsync` and `flushDebugLog`. Synchronous helper forms remain available for existing integrations
- `atomic worker status` and the `workflow` tool's `status` action show the fleet controller, its latest scale events, the fleet-wide rate limits and each worker host's checkpoint shipping lag, and when each running child last recorded a step. `atomic worker metrics` caps the hosts it asks for at the capacity estimated from recent calls and worker time not spent waiting for tokens, holding limited growth at the current host count while a minute of history warms, and exports the combined capacity across every root as `rateCapHosts` and `atomic_fleet_rate_cap_hosts`, even when it does not reduce the target. An unused scope releases its hold after a minute without draws while its roots run children, not while its first host is booting or its claimed children are restoring their workspaces. Only started attempts contribute busy time to the estimate; bucket movement that reveals uncounted draws from older hosts disables that scope's cap for the observation window. See [The scaling signal](https://github.com/bastani-inc/atomic/blob/main/packages/coding-agent/docs/guides/worker-hosts.md#the-scaling-signal) ([#4768](https://github.com/bastani-inc/atomic/issues/4768))
- `resolveAutoModel()` from `@bastani/atomic` returns the model and thinking level `model: "auto"` stands for, from the settings, the models that have credentials and the current session's model, without any model request
- `createAgentSession({ intercom: { group, reachable } })` gives a top-level session its own Intercom home group, ahead of `ATOMIC_INTERCOM_GROUP`, Intercom `config.json` and the project group, and the other groups it may reach; the session keeps its workflow extension. It lists, sends to, asks and joins only within those groups, can't leave its home group, and reach is one way, while replies to its asks still arrive. `session.intercom.setReachable(groups)` changes the reachable groups on the live session from its next Intercom call. Its workflow stages and subagents reach only their own groups, and the Intercom broker enforces the policy. ([#5352](https://github.com/bastani-inc/atomic/issues/5352))
- Added `Selector`'s `closeOnSelect` option for persistent single-select pickers, `retrySelection()` to reopen a picker after a failed choice, and item `searchTextMode: "replace"` to search only explicit `searchText` instead of displayed labels, descriptions and tags ([#5224](https://github.com/bastani-inc/atomic/issues/5224))
- Added `AgentSession.setModel(model, { thinkingLevel })` to set a model and its reasoning level in one call. Unsupported levels clamp to a supported level, and `persist: true` saves both. RPC `set_model` also accepts `thinkingLevel` and rejects unrecognized values without switching the model. `RpcClient.setModel(provider, modelId, { thinkingLevel })` sends the option. Persisted `set_model` and `cycle_model` responses include `persistedDefaults` to distinguish saved startup preferences from session-only changes ([#5224](https://github.com/bastani-inc/atomic/issues/5224))
- Added RPC `set_scoped_models` to replace the session's model-cycling scope and optionally save global model patterns through `enabledModels`. Scoped model searches and `cycle_model` use the updated list immediately ([#5224](https://github.com/bastani-inc/atomic/issues/5224))
- `ATOMIC_STARTUP_TRACE` names a file to which Atomic appends each startup milestone (process start, first paint, engine ready, first provider request) with its wall-clock time; an interactive session's engine writes to the same file
- `ensurePrivateTempDirAsync()` and `assertPrivateDirectoryAsync()` for extensions and SDK integrations: they create or check a directory private to the current account without blocking, waiting for the Windows owner and access-list check ([#5285](https://github.com/bastani-inc/atomic/issues/5285))

### Changed

- SDK: a blueprint build's trust check (`BlueprintBuildConfig.trusted`) may return a promise
- An edit preview or result whose change needs more than 256 line edits shows the changed block replaced as a whole, and a modified line that differs by more than 64 word edits is shown without word highlights, instead of freezing the interface while the full diff is computed
- On Linux, starting a shell or one of Atomic's own processes (worktree snapshot Git, `pi.exec`, the search tools' `rg` and `fd`, worktree setup) no longer pauses Atomic for a time that grows with its memory. Each start copied the whole process with `fork()`, which took about 65 ms per GB it held. A session holding 8 GB that started five processes a second kept its main thread busy 99.9% of the time, so subagents took minutes to start and the screen and Intercom lagged; it now stays under 2% at any size. `ATOMIC_HOST_SPAWN=child-process` restores Node's `child_process` for Atomic's own processes.
- Hosts running many agents stay responsive while they record worktree snapshots. A turn whose checkout did not change now starts 9 Git processes instead of 14, a changed one 17 instead of 21, and sessions that capture the same checkout at the same time compute its tree at most twice instead of once each. Each snapshot still records the checkout as it was after its turn.
- Interactive startup no longer waits for its engine: the first frame, with an editor that takes input, appears while the engine still loads, and a host on a terminal starts the engine as it starts itself, so a prompt typed at launch goes out sooner. The standalone binary paints its first frame in about 270 ms instead of 940 ms on Linux and in about 450 ms instead of 1,290 ms on Windows; the npm package in about 940 ms instead of 1,570 ms on Linux and 2.3 s instead of 4.3 s on Windows
- The standalone binary for the build's own platform (Linux x64, Windows x64) ships a bytecode cache of its application bundle, so every process it starts, including `-p`, `--mode rpc`, subagents and workflow workers, loads in about 150 ms instead of 360 ms
- On Windows, finding PowerShell on `PATH` no longer starts `where` and waits for it, which cost every start about 25–40 ms before its first frame
- A background shell a subagent starts now belongs to that subagent. Its completion notice reaches only the subagent: while it runs, through its wake while it is released, and otherwise when it next runs. It is never sent to the chat or workflow stage that launched the subagent. The shell is listed in the subagent's own `/tasks`, not the launcher's, though it still runs in the launcher's task owner, so it outlives the subagent and Ctrl+X Ctrl+K still stops it ([#5342](https://github.com/bastani-inc/atomic/pull/5342))
- Tasks that finish together reach the model in one request that starts one turn, instead of one turn each. A notice that arrives while the chat is working is read at that turn's next safe point and starts no turn of its own. Each finished task now shows as one line, such as `● Background command "npm test" completed (exit code 0) · 12s` or `◼ Task "sleep 300" was stopped by the user`, the same in the main chat, workflow stage chats and subagent views. Ctrl+O shows a shell's last output lines and an agent's full result ([#5342](https://github.com/bastani-inc/atomic/pull/5342))
- Clarified in `codemode`'s description, system-prompt guidance, and `searchTools()`/`describeTool()` hints that `subagent`, `workflow`, and other model-only tools (plus `intercom`'s model-only actions) cannot be called from inside a `codemode` script, and should be called directly as separate top-level tools when available in the session
- `openNodeSqliteDatabase` and `wrapNodeSqliteDatabase` connections hold a shared lock on `<file>-open.lock` while they are open, `file:` URIs included, so Atomic removes a local checkpoint journal only when none of them has it open. An `openNodeSqliteDatabase` read-only connection takes the lock only beside a database that has a `<file>-holders` directory, a `<file>-open.lock` or a `<file>.lock` file, and goes without it where it cannot create the lock file, such as in a read-only directory. Wrapped file-backed connections attempt the lock even for an untouched read-only database, because the caller's connection does not expose its read-only setting. Wrapping also works without the lock when the lock file is not writable, including when a Windows directory's permissions refuse new files ([#5317](https://github.com/bastani-inc/atomic/issues/5317))
- `SessionStartStep` has a `registering-intercom` step, for a subagent start that waits for its Intercom registration, and `sessionStartStepText(step)` describes a step in words. `SubagentChildPolicy.startup` gives an extension the child's start signal, lets it name the step the start waits in, and says whether the child has yet to start its first turn.
- Pool operations that wait for another process's lock now poll every 50 ms for up to 60 seconds, allowing a stopped holder's lock to expire after 30 seconds. Parking a seed polls at the same cadence for up to 120 seconds. Cancellation interrupts lock retries while a resume acquires a pool slot or adopts a seed, and while a prebuild acquires a pool slot. Ownership updates and cleanup finish before cancellation returns ([#5320](https://github.com/bastani-inc/atomic/issues/5320))

### Fixed

- Model searches initially select the best match, and effort arrows work with SS3 terminal key sequences. Provider searches no longer match sign-in status or method text. Long dialog titles and options wrap instead of losing text, and selector hints show only available actions ([#5224](https://github.com/bastani-inc/atomic/issues/5224))
- Isolated `/scoped-models` changes update both model searches and Ctrl+P cycling. Scope saves run in order and report failures, and engine reconnection no longer overwrites a newer model or reasoning choice. RPC model responses report saved defaults only for `persist: true` ([#5224](https://github.com/bastani-inc/atomic/issues/5224))
- Pickers ignore a repeated Enter or click instead of answering twice, and an extension dialog shown again after another dialog repaints in the current theme. Ctrl+C cancels a filtered picker with Kitty and modifyOtherKeys keyboard protocols too; `/scoped-models` keeps its clear-search-first behavior ([#5224](https://github.com/bastani-inc/atomic/issues/5224))
- Isolated interactive mode applies the reasoning level chosen in `/model` and keeps model and reasoning changes made by extensions during `/model` or Ctrl+P without saving session-only changes. Saving a model choice no longer copies project model defaults or scoped-model lists into global settings ([#5224](https://github.com/bastani-inc/atomic/issues/5224))
- A prompt typed while Atomic starts is no longer sent twice on Windows: a stray cursor report reached the startup input as F3, left a "C" in the editor and sent it with the next prompt. F1–F5 and Page Up/Down sent as `ESC [ [ …` no longer type a letter into the startup input
- Keys typed while Atomic started are no longer lost when a startup dialog (project trust, dirty checkout, first-run setup) takes the terminal: they are captured as the draft, and keys typed once the dialog holds the terminal reach the dialog
- Restoring saved model catalogs at startup no longer fails while another Atomic process saves its catalog, and no longer takes the save lock once per provider, which cost about 180 ms before the first frame on Windows
- On Windows, saving credentials or a refreshed model catalog no longer fails with `EPERM`, losing the save, when another Atomic process is reading `auth.json` or `models-store.json` at that moment: the save waits for the read to finish
- The main chat no longer receives the completion notices of shells it never started. A subagent's shell that finished after the subagent ended, was stopped or could not take the notice reported to the main chat, and so did a workflow stage's shell whose notice was still being written when the stage closed, each starting its own turn there. The main chat's `/tasks` also listed every subagent's shells ([#5342](https://github.com/bastani-inc/atomic/pull/5342))
- Model chains skip providers without credentials before sending a request, and skip every remaining model of a provider after it rejects credentials. A pinned model with no fallbacks is never replaced, and missing-credential errors name the affected models and providers ([#5353](https://github.com/bastani-inc/atomic/pull/5353)).
- Fixed sibling agent directories under one parent, such as `ATOMIC_CODING_AGENT_DIR=/x/a1` and `/x/a2`, sharing one session, workflow, pool, artifact, workspace and Intercom store in `/x`: the default `~/.atomic/agent` keeps its store at `~/.atomic`, while custom agent directories store under `<agentDir>/workflows` and resolve relative storage and secret paths against `<agentDir>`. One eligible agent directory can adopt an existing parent store once, with a one-time notice, and `atomic storage status` shows the resolved path without creating a missing agent directory. Concurrent processes of one directory keep the same store across restart. Distinct existing parent-relative targets remain readable, including explicit JSONL session directories beside older local sessions when another profile adopted worker-host state first. Siblings selecting the same target stay isolated, including through symlinks or hard links. History stays accessible after an adopting directory or its parent is renamed or moves across filesystems, including through symlinks or junctions, for never-created SDK agent directories beside ordinary source folders, and on filesystems without hard links. An identifiable original retains its adopted default store when copied, and copies keep their own history after the original is removed, including history in a newly configured database with a parent counterpart. An adopter reopened after a move keeps its history when later copies use its former name. When an original and its backup cannot be told apart, neither uses the parent's default store, even if the original starts first. If the physical parent holds the adopted store, the first to claim the parent-relative session directory keeps those sessions, including when opened through a symlink or junction. To keep both the parent's default store and its sessions, start Atomic once after moving and before copying. Default storage and relative-target ownership follow the current home when the default agent directory is moved or mounted elsewhere. Read-only agent directories can use writable storage without saving a new home decision. A writable agent directory no longer needs a writable parent just to select its own store, and changing `HOME` cannot expose an existing default agent's store to a custom profile. Prior-use detection no longer overlooks established profiles in large directories, and repeated storage lookups and resource discovery are faster without delaying token-file changes ([#5242](https://github.com/bastani-inc/atomic/issues/5242))
- A fast foreground shell command no longer delivers a stray `Background shell completed` notice after its own result when the command exits before Atomic has finished starting it. The model was shown the command's result a second time, as a background shell's, in chats and workflow stages alike ([#5333](https://github.com/bastani-inc/atomic/pull/5333))
- The interface and its engine no longer stop responding while Atomic reads or writes files and runs short commands in the background of a session: settings, credentials, project trust, keybindings and debug logs; session lists, headers, claims and markers; skills, prompts, themes, context files and resource reloads; package installs and updates; tool artifacts, archives, notebooks and todos; blueprint builds and workspaces; switching, forking or starting a session; private temp directories, their cleanup and tool output spilled to disk; finding the shell for the bash and PowerShell tools; worktree snapshots, their restores and LFS downloads; git lookups for the footer and worktrees; the clipboard, the external editor, `/export`, `/share`, `/changelog` and `/import`; the summary of a branch left in `/tree`; MCP configuration, logs and OAuth locks; and model catalog refreshes. Each now runs without blocking the event loop, so typing, rendering and streamed output keep going
- SQLite writer queue checks, lock records, writer hand-offs and open-lock cleanup no longer block the interface. A transaction waits for its hand-off, and closing waits for pending lock records before releasing its open lock
