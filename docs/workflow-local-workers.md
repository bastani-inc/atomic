# Local workflow workers

Issue #3869 enables an explicit public opt-in to local workers through SDK options and workflow settings. Without `localWorkers`, ordinary runs create no pool tables, worker processes, or polling loops. The public usage boundary is documented in the [workflow operations guide](../packages/coding-agent/docs/workflows/operations.md#local-workflow-workers).

Placement is limited to local Linux and macOS processes with native process identity and boot identity. Windows and hosts without those identities refuse activation, even when no process admission limit is configured. This prevents treating an expired lease as proof that an old process tree stopped. Remote workers are not supported.

## Execution and persistence

`workers/local-pool.ts` binds a supervisor to one physical `JournalDurableBackend`. The root keeps its existing execution lease. The existing durable child wrapper validates the boundary identity; `engine/primitives/workflow.ts` dispatches first-level children through the supervisor. Nested children execute on that same worker through the ordinary engine and scoped backend.

A headless Node process loads `workers/local-worker-entry.mjs`, then calls the existing `engine/run.ts`. It uses the normal Atomic agent-session adapter. It receives the original child run ID, parent boundary, root ID, depth, cwd and checkpoint scope. Its journal view refuses root registration, lease acquisition and direct journal writes.

Workers poll the supervisor over IPC. The supervisor claims work and applies checkpoint/session operations through the fenced SQL queue. IPC is transport, not completion evidence. The root reads completed results from the SQL result record. Session creation, append and replacement write a stage checkpoint and transcript in the same fenced transaction; no worker transcript is recovered from a JSONL path.

Checkpoint completion timestamps come from the worker's JavaScript clock. The coordinator allows them to be up to one second ahead of its JavaScript or SQLite clock. This covers Windows timer-tick differences between processes and SQLite's coarser clock without accepting clearly future timestamps. Lease fencing, event timestamps and commit receipts still use SQLite time only; the stored checkpoint timestamp remains unchanged for replay.

The pool gives the coordinator lease three root-heartbeat intervals, leaving room for delayed renewal. After a worker exits, the coordinator drains its received IPC operations and checks durable completion before applying the retry limit. A completion already in flight can still succeed on the final attempt.

Worker exit triggers a bounded replacement. Expired work becomes claimable only after the local worker has exited. Each child has a three-attempt limit per root incarnation; successful recovery of one child does not exhaust retries for later children. A child that loses its third attempt fails alone with a retryable `worker_retry_limit` error naming its child run and definition export; its work row ends `failed` and the pool and its other children keep running. Only workers that keep crashing without work (more than three replacements in a row), worker startup failures, unexpected coordinator errors and the coordinator's own death fail the whole pool. When a pool closes without a quit, work its root left unfinished (`ready`, or `leased` by this incarnation) also ends `failed`, except quarantined attempts, which keep their leases; a resumed root that enqueues failed work again replays it. Replacement workers replay the child from acknowledged checkpoints, including completed stages and nested children. An unfinished agent stage resumes its SQL session. External effects that precede a checkpoint can still repeat.

Resuming a root releases the work its previous incarnation leased, but a released child becomes claimable only when the resumed root enqueues it again; until then its row keeps the previous root epoch, and claims select only rows of the current epoch. The root accepts activity only for work it has enqueued, so an earlier claim would be rejected as a stale lease. A pool that has failed or quit stays bound to its root until its owner closes it: a child the root starts afterwards gets the pool's failure (or suspends after a quit) and never runs in the root process, whose session store cannot see pooled stage sessions.

The three-attempt limit counts attempts within one root incarnation: the coordinator records each work item's generation when the root enqueues it and counts from there, so earlier incarnations' attempts do not count. A refusal with `Stale work lease` is a typed fence (`fenced: true` on the worker reply), not a worker fault. The worker ends that attempt, reports `fenced`, and claims new work; the coordinator leaves superseded work with its current owner and counts nothing. An exit whose attempt was already superseded does not count toward the limit either.

## Compatibility boundary

The internal inventory accepts definitions loaded through the shared workflow-module loader, with an absolute module path, export name and SHA-256 content digest. Unregistered closures, changed entry modules and process-bound run adapter overrides fail before a worker starts. Child invocation budget overrides are also rejected before enqueueing; they are not silently dropped. The entry-module digest is not a deployment system or a transitive dependency snapshot. All workers still use the coordinator's local installation and filesystem.

The pool shares the root's SQLite file only when the journal is the default-prefix local SQL journal. Any other journal runs through the coordination database described under [Journals in another database](#journals-in-another-database). Admission and budget accounting are shared with the root. The root persists effective worker and admission settings and refuses changed settings or entry-module digests during resume. The digest covers only the worker entry file, not imported dependencies. `localWorkers.startupTimeoutMs` is operational rather than placement configuration: it is stripped before the effective resources are persisted and compared, so roots saved before the field existed resume unchanged and the timeout can be changed between resumes.

## Journals in another database

The pool's queue, leases, usage, admission permits and pooled-stage sessions need one database every pool process opens, and the pool's SQL joins the root's run status and lease with them in one transaction. That holds when the root's journal is the default-prefix SQLite file, and the pool then shares it. A journal that is a libSQL or Turso database, a custom-prefix file, or any other run-journal adapter, including one that implements `RunJournal` without being a `SqlRunJournal`, keeps the root's durable record where it is, and the pool keeps its machine-local state in a **coordination database**: a SQLite file on the coordinator's machine, `<agent dir's parent>/workflows/pool/<hash of the journal selection>.sqlite` (`~/.atomic/workflows/pool/` by default). The hash covers what makes the selection open that database: the adapter module, its options (a URL, a namespace), its prefix and the agent directory. It leaves out where an adapter reads its credentials from, so the same token read from another environment variable finds the same pool state. Every worker is a child of one coordinator on one machine, so none of that state needs to be remote. One coordination database serves every root on a journal, so a root resumed on this machine reopens it, `admission.userLimits` counts across those roots, and worker logs sit beside it. `workers/pool-journal.ts` owns the selection, the path and the registry that routes a journal to its coordination database.

Every pool process opens the durable journal itself, from the storage selection the root opened it with (`runJournalOrigin`, recorded by `openSelectedRunJournal`). The selection travels as JSON with binary and bigint adapter options tagged, and carries no secret value: an adapter's `secrets` are environment or file references that each process resolves. The coordinator receives it in its `prepare` command and workers receive it in `ATOMIC_POOL_DURABLE_JOURNAL`, which the worker deletes from its own environment after reading it, so the tools it starts do not inherit it. It is never in argv. A journal passed to the SDK as an object, a memory journal and an open database cannot be opened by another process and are refused with the reason.

### Keeping the two databases consistent

`PoolRemoteJournal` keeps the coordination database's run and lease rows for the root equal to the journal's: its status, the holder, the epoch and the lease's age on the journal's own clock. The queue reads those rows exactly as it reads the journal's own tables for a local journal, so every fence it applies (root lease, work lease, generation, worker, epoch, root status) is unchanged. The rows are refreshed before queue operations when they are two seconds old and every ten seconds by the coordinator. The copy's age is counted from the moment the read started, plus the journal's own `ageMs`, so a slow answer or a wait for the local write lock can make a lease look older than it is by up to a round trip and never newer. A lease the journal handed to someone else raises `StaleLeaseError` at once and the pool refuses everything the old holder asks. An unreachable journal leaves the last copy to lapse inside the coordinator's 90 s lease window, as an unrenewed root lease does.

A checkpoint commit used to validate, apply the session it carries, bill usage and record the event in one transaction. With two databases it is three steps:

1. One local transaction runs every check the single-database commit runs, validates the checkpoint, applies the session, bills the usage and records the accepted event in the outbox (`<prefix>_pool_outbox`). This is the commit point: a stale, fenced or superseded attempt is refused here and nothing exists for it.
2. The event goes to the durable journal through its idempotent `append`, keyed by the checkpoint's event key. A key is recorded once and answers `exists` with the first event afterwards, so repeating the step after a crash or a lost reply finds the same event.
3. One local transaction stores the receipt (the journal's sequence and time) as the operation's result and deletes the outbox row.

Every crash window is recoverable and none loses or duplicates an event:

- Before step 1 commits nothing was accepted. The worker's retry of the same operation runs step 1.
- Between steps 1 and 2 the journal has no event, and the pool has an outbox row. The same operation retried, the next claim and the next coordinator's `prepare` all deliver outbox rows first. A claim hands out no work while it cannot deliver them, or while another delivery pass is still running (a pass clears the pending flag when it starts, not when it ends, and a commit can stage a row after the pass has read its rows, so a claim waits and looks again), so a replacement attempt always replays a journal that holds what the attempts before it were told is committed.
- Between steps 2 and 3 the journal has the event and the outbox row remains. Delivery finds it (`exists`), takes its sequence and time, and finishes step 3.
- A worker fenced after step 1 does not lose its accepted event: the event is delivered and the replacement attempt's own commit of the same key answers `exists`.
- Duplicate in-flight deliveries of one operation share one journal write. The same operation with another request is refused as an identity conflict, and a different checkpoint already under the key is a conflict that applies nothing.
- A child cannot complete while its outbox rows exist, because the child's result is its journal checkpoint.
- If the root lease was lost before step 2, the append fails with `StaleLeaseError`. The outbox row stays until a holder of the root drains it, and a resumed root's coordinator delivers it under its own epoch.

A boundary's start is written to the journal first and the work row second, because a crash between them is repaired by the root's resume enqueueing the boundary again, which finds the start recorded. Validation reads the root's checkpoints through the journal's `read`, from the checkpoint index's watermark and outside any transaction, so nothing waits on the network while holding the local write lock. A read takes the watermark once, when it starts: other commits' reads fold into the same index while it waits on the journal and move the live watermark, and verifying against the moved one counted rows twice (`Pool boundary scope: boundary has no unique start record`, seen only at 80 ms round trips and up). The index starts over when the event at its watermark is gone or replaced.

### Known limit: stage message receipts

When a worker's stage session takes a queued Intercom message, the root then records that delivery as a journal event (`recordPendingStageMessageDeliveries`, or `markPendingStageMessageDelivered` for a direct message), and the pool guards that write with the attempt's work lease. On a journal that is a default-prefix SQLite file the guard runs inside the append's own transaction, so a receipt is never recorded for an attempt the coordinator fenced before the receipt committed. On a journal in another database the guard cannot join the journal's transaction. It runs twice, right before the append starts: the in-process fence flag the root keeps from the coordinator's ordered events, and the attempt's work row in the coordination database. A fence the coordinator commits after those checks and before the journal's append returns is not seen.

What that leaves: the message stays recorded as delivered although it reached only the session of the attempt that was fenced, so the replacement attempt's stage is not offered it again. The window is one journal `append`, so it grows with the journal's round-trip time; it needs a worker declared lost (an exit, or a missed lease) in that same interval. A fence before the checks refuses the write, and so does the in-process flag.

Why the interface does not close it: `RunJournal.append` takes `expectSeq`, which is a condition on the root's own history (the head sequence), not on the pool's work row in another database, and a journal adapter cannot evaluate a condition on a database it does not own. Closing it needs the pool to pin the attempt for the duration of the append, for example an in-flight row in the coordination database that `expire`, `releaseExited`, `failExited` and `releaseClosed` wait on or refuse while it exists, with a bound for a root that dies mid-append. That changes every fencing path and the coordinator's recovery tick, so it is not part of this change. Checkpoint commits do not have this limit: their journal write is ordered after the acceptance transaction and recovered by the outbox.

### Resume and other machines

The root records the host that owns its coordination database (`resources.coordinator.host`, a random id kept in `<agent dir's parent>/workflows/pool/host-id`) and the database's name (`resources.coordinator.database`). Resuming on the same machine reopens the same coordination database and replays children as in the single-database case. A resume whose journal selection now maps to a different database name, because the adapter, its options, its prefix or the agent directory changed, is refused with an error naming both: it would find an empty queue and run the root's children again beside whatever the old database still holds. Resuming on another machine is refused with an error that names the recorded host: the work queue and leases are in a database that machine cannot see, and its workers may still be running children. Resume the root on that machine. Deleting a run from the journal does not delete its rows in the coordination database.

`admission.userDatabase` must be omitted for such a journal, or name the coordination database; user limits then count in it.

## Worker failure containment (#3887)

A worker can die while the coordinator still owes it IPC replies; workers keep renewal, control, usage and activity requests in flight. `ChildProcess.connected` stays true until the coordinator reads the IPC EOF, so a reply sent in that window fails synchronously with `EPIPE`. Without a send callback, Node reports that on the `ChildProcess` `'error'` event, and the second such error after the one-shot startup listener crashed the root. Every coordinator `send` now passes a callback, and the `'error'` listener is permanent. A failed reply or channel error kills the worker once, which routes it into the existing exit path: the attempt is fenced, process cleanup is confirmed, and the child is replayed on a replacement worker.

Worker standard error is piped to `worker-logs/<encoded root id>/<worker id>.log` beside the database that holds the pool's tables (the journal file, or the coordination database), while an 8 KB tail stays in memory for error messages. Startup failures are reported on the child `'close'` event, after standard error is drained, so the message tail is complete. `Local worker exited before readiness`, `Local worker startup timed out after <n> ms` and `Local worker retry limit` name the log file. Logs of workers that exit on their own, time out or are killed by stalled-lease recovery are kept. On a successful pool close, logs of the workers that close stopped are deleted and the root's log directory is removed if empty; a coordinator crash leaves every log in place.

A worker opens its read-only journal backend without folding any run, reports ready, and only then folds the served root. Readiness therefore costs the same on an empty journal and on one with hundreds of unrelated runs. The root is folded before the first claim, so a large root history is read before the worker holds a work lease rather than inside the five-second lease window. `start()` resolves when any worker is ready (`Promise.any`) and fails with the first startup error only when every initial worker fails. Initial workers that fail later are dropped without failing the pool; a replacement that cannot start still fails it, as before. Pause, resume and quit wait only for acknowledgements from ready workers, because a still-starting worker observes the current control revision as its first request after readiness.

### Incremental root hydration

Workers used to call `hydrateWorkflow(root)`, which rebuilds the root from seq 1, after every commit and every claim. They now call `catchUpWorkflow(root)` at those points and before each claim request. It is the same prefix-checked fold used by the resume catalog: it reads from the last folded seq, folds the appended entries when that entry still has the folded `seq` and `at`, and otherwise rebuilds. This is equivalent to a rebuild because:

- a run's journal events are append-only with strictly increasing `seq`; `deleteRunData` is the only operation that removes events, and it removes the whole run;
- a deleted and recreated run is detected because its entry at the folded `seq` is missing or has a different store timestamp, which forces a rebuild;
- `fold` is deterministic and skips entries at or below the folded `seq`, so folding a suffix onto the cached prefix produces the state a full fold would;
- nothing else mutates the worker's projection: the worker backend proxy refuses every mutating method and its journal proxy is read-only, so the cached prefix can only come from earlier folds.

The coordinator still rebuilds the root through `hydrateWorkflow` before enqueueing a child and after reading its result.

### Admission defaults

A public pool without `admission` still passes `{}` to the coordinator and workers, so each opens `SqlResourceAdmission`. This is intentional. A limit-less admission writes no limit rows, but every managed tool process still takes a process permit bound to its Unix process group. When a worker exits, the coordinator's `releaseStoppedSessions(worker)` reconciles those groups. Live groups left by the exited worker belong to its fenced attempt, so the coordinator reaps them with `reapStoppedProcesses(worker)`. It sends SIGTERM to each bound group on this host, then SIGKILL after `REAP_TERM_GRACE_MS`, then waits at most `REAP_KILL_GRACE_MS` more. A group that is gone, or holds only zombies (which hold no resources), has its permit released. Only the kernel decides that a group is gone (`kill(-pgid, 0)` fails with `ESRCH`). A group holds only zombies when two consecutive complete scans of the process table (`/proc`, or `ps` elsewhere) find the same non-empty set of members, all zombies. An empty, partial, failed or changing scan counts as alive. One child's surviving groups never count toward the pool's idle-worker retry limit. The worker's work stays leased while it is reaped: recovery extends that lease instead of expiring it, including when recovery itself stopped a stalled worker, so no other worker can claim the child and replay it alongside the old processes. Beyond that in-memory hold, recovery never expires an attempt, and a resumed root's coordinator never releases an earlier incarnation's attempt, while any of that attempt's bound process permits is granted for a process group not confirmed gone. This is read from the journal (`unconfirmedProcessGroups`), so the quarantine holds across restarts and durable resume. A resumed coordinator reaps a retained attempt's groups on this host with the same bounded SIGTERM, then SIGKILL, sequence (`reapProcessGroups`). If they are gone, it releases the attempt. If any survive, only that child fails with the retryable `worker_cleanup_unconfirmed` error naming them, and the attempt stays quarantined. Groups on another host cannot be signalled or probed, so their attempt stays retained until recovery confirms them gone. A released retained attempt is claimable only in the current root epoch: if the resumed root already enqueued it while it was leased, which cannot adopt leased work, the coordinator recorded that enqueue and the release adopts it into the current epoch (`releaseRetained`); otherwise the root's later enqueue adopts it, as for any released earlier work. Attempts of a retained child count from its retained generation, per the per-incarnation attempt rule. If every group is gone, the child replays on a replacement. If a group is still alive when the bound expires, only that child fails, with a retryable `WorkflowInfrastructureError` (`worker_cleanup_unconfirmed`) that names the surviving process groups. Their permits stay quarantined, and the work stays leased for the pool's lifetime, so it never replays alongside them. One worker's leftover groups never fail the rest of the pool. Permits never bound to a process group stay quarantined. Close reports cleanup that is still unconfirmed, whether the reap ends during close or finished before it: it re-checks the groups that survived earlier reaps. Attempt fencing (`assertCurrentAttempt`) also refuses new sessions and processes from a stale attempt, and grants wait while the root is paused. Without the admission, a worker's permits would be no-ops without `bindProcess`, and a dead worker's orphaned tool processes could overlap with its replay.

## Control and routing

Root control is registered before asynchronous pool preparation. Pause, resume and quit intent has a durable revision. Claims and resource grants check that intent; workers acknowledge revisions after applying the existing scheduler and stage controls. Pause waits for worker acknowledgements before publishing the root as paused. Quit gives workers a bounded chance to suspend and dispose their sessions, then confirms local process cleanup or reports unresolved cleanup. Explicit resume reopens admission without changing queued work identities or completed child results.

Resume checks for a newer pause after durable persistence, before reopening pool admission. Pool shutdown releases Intercom routes even when worker or session cleanup fails, while still reporting the cleanup error.

Worker activity updates the existing root store, including nested parent edges and worker lease diagnostics on stages. Workers do not register additional durable roots. The root's Intercom route owner announces worker stages and supplies their current route capabilities. Replacement rotates those capabilities. Pending direct messages, sticky broadcasts and delivery receipts use the existing root-owned durable queue. A worker never writes the root message ledger directly.

Worker activity publication keeps one request in flight and coalesces later invalidations into the latest snapshot. Lease renewal and control polling do not wait for activity acknowledgements. Pending-message transitions apply persisted messages to the current run snapshot, including when worker publication replaces it during persistence.

The root records a receipt only after transport acknowledgement or confirmed context admission. Each receipt append validates the work lease in the same SQL transaction as the write and checks the published session before the transaction returns. A concurrent replacement either precedes that validation and rejects the receipt, or follows the receipt's transaction ordering. Successor delivery waits for the old drain to release its message claim. Session replacement rejects old readiness requests and discards the failed delivery object. A temporary coordinator heartbeat lag refuses receipt commits without retiring the root's journal backend.

The root reconstructs committed child checkpoints and pending messages from the journal. Uncheckpointed worker activity is observational and may disappear on recovery. Recovery still provides at-least-once execution, not exactly-once external effects.

## Public placement and admission

The public SDK accepts `RunOpts.localWorkers: { count, definitions: [{ path, exportName }], startupTimeoutMs? }` and optional `RunOpts.admission`. The SDK helper `loadWorkerWorkflow(absolutePath, exportName = "default")` loads an importable child definition for `ctx.workflow(child)`. A root can remain an inline closure, but each eligible child definition needs an importable path and export inventory. Only the complete first-level child subtree runs on a worker; nested children remain there. Missing or incompatible definitions fail instead of falling back to local execution. Independent stage placement is not supported.

The CLI reads the same keys from `workflows` settings. Settings and entry-module digests are retained with the root. Settings paths resolve against the invocation working directory; SDK paths resolve against `cwd`. Arbitrary SDK process-bound adapters, UI, persistence, and related runtime overrides are rejected before worker launch. CLI host bindings stay in the root process; worker stages create their own sessions.

Resource limits count agent sessions from creation through disposal, including fallback and delegated sessions, and Atomic-managed tool processes until cleanup is confirmed. Yielding an observation does not free a process permit. Arbitrary subprocesses outside managed Atomic APIs are not counted. Host load and free-memory thresholds are launch gates, not hard OS limits. Optional user-wide limits require all participating roots to use the same canonical local SQLite path, or, for roots on a journal in another database, this machine's coordination database. This is local-user coordination, not multi-tenant isolation.

Recovery is at least once: committed checkpoints prevent repetition of completed work, but external effects performed before a checkpoint may run again. Use stable logical idempotency keys where duplicate effects matter. Root status, stages, steering, pause, quit, and resume still operate on one root identity.

The worker entrypoint ships in installed workflow bundles. The standalone launcher handles its internal worker mode before loading the normal CLI, supplies the same host modules as the app bundle, and refuses startup without an IPC channel.
